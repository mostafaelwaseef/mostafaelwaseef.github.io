Lab 4 — Web Shell Upload via Extension Blacklist Bypass

🔴 Critical 📅 2026-08-03

📋 Finding Summary

FieldValue
TypeWeb App
Severity🟣 Critical
CVE / CWECWE-434, CWE-16
Date2026-08-03

🔍 Description

The avatar upload functionality restricts certain file extensions via a server-side blacklist, blocking direct uploads of .php files. However, the server does not restrict uploads of Apache configuration files. By uploading a .htaccess file containing AddType application/x-httpd-php .xyz into the avatars/ directory, an attacker can instruct Apache to treat any file with the .xyz extension as executable PHP. A subsequent upload of a PHP web shell named exploit.xyz — an extension absent from the blacklist — is accepted without restriction. Requesting the uploaded shell causes Apache to execute it, returning the output of arbitrary server-side code.

🎯 End Goals

  • Bypass the .php extension blacklist to upload an executable PHP web shell.
  • Use a .htaccess file to register a custom extension as a PHP handler in the upload directory.
  • Execute the web shell via a GET request to read /home/carlos/secret and submit it to solve the lab.

🪜 Steps to Reproduce

  1. Log in as wiener and navigate to the My Account page.
  2. Upload a benign image to confirm the upload mechanism and identify the serving path.
  3. Inspect Burp traffic to locate the upload endpoint and the URL path from which uploaded files are served.
  4. Attempt to upload a PHP web shell directly to confirm that .php is blacklisted.
  5. Craft a .htaccess file that maps a custom extension (e.g. .xyz) to the PHP handler and upload it to the avatars/ directory.
  6. Upload the PHP web shell with the custom extension — confirm the server accepts it.
  7. Issue a GET request to the uploaded shell’s URL to trigger PHP execution and retrieve the secret.
  8. Submit the secret to solve the lab.

🧠 Analysis

Step 1 — Lab setup — logging in and locating the avatar upload form

Navigated to the lab and logged in with the provided credentials (wiener). The My Account page at /my-account presents an avatar upload form that posts files to /my-account/avatar as a multipart request.

Step 2 — Upload a benign image to confirm the upload mechanism

Selected image.jpeg and clicked Upload. The server responded with “The file avatars/image.jpeg has been uploaded,” confirming files land in an avatars/ subdirectory. The account page then rendered the image as the current avatar.

Step 3 — Inspect Burp traffic to identify the upload and file-serving paths

In Burp Proxy HTTP history, the POST to /my-account/avatar confirmed the Content-Disposition filename parameter and the avatars/ upload path. The server header revealed Apache/2.4.41 (Ubuntu). Inspecting the subsequent GET /my-account response body revealed <img src="/files/avatars/image.jpeg">, confirming that uploaded avatars are served from the /files/avatars/ URL path.

Step 4 — Attempt direct PHP upload — blocked by blacklist

Selected exploit.php containing <?php echo file_get_contents('/home/carlos/secret'); ?> and submitted the upload form. The server responded with HTTP 403 and the message “Sorry, php files are not allowed.” Burp confirmed the rejected request: filename="exploit.php", Content-Type: application/x-php, HTTP 403 Forbidden. The .php extension is explicitly blacklisted.

Step 5 — Upload a .htaccess file to register a custom extension as PHP

In Burp Repeater, crafted a multipart upload request with filename=".htaccess" and Content-Type: text/plain. The file body contained AddType application/x-httpd-php .xyz, instructing Apache to treat any .xyz file in that directory as PHP. The server accepted the upload with HTTP 200: “The file avatars/.htaccess has been uploaded.” Apache will now parse .xyz files through the PHP engine when requested from /files/avatars/.

Step 6 — Upload the web shell with the custom extension

In a second Repeater tab, sent the same multipart upload with filename="exploit.xyz", Content-Type: application/x-php, and body <?php echo file_get_contents('/home/carlos/secret'); ?>. The .xyz extension is not on the blacklist, so the server accepted the file with HTTP 200: “The file avatars/exploit.xyz has been uploaded.”

Step 7 — Execute the web shell and retrieve the secret

Issued a GET request to /files/avatars/exploit.xyz. Apache looked up the .htaccess mapping, identified .xyz as PHP, and passed the file to the PHP engine. The response returned HTTP 200 with Content-Length: 32 and the contents of /home/carlos/secret: JzcYvoN3pnteyD86y6mWhH77gPUYD0su

Step 8 — Submit the secret and solve the lab

Submitted JzcYvoN3pnteyD86y6mWhH77gPUYD0su via the lab’s Submit solution button. The lab confirmed the value was correct and marked the lab as Solved.

🎯 Impact

An attacker with upload access can plant a .htaccess file that reconfigures Apache’s MIME type mappings for the upload directory, then upload a web shell under any invented extension not covered by the blacklist. This achieves server-side PHP execution under the web server’s process context, enabling arbitrary file read (demonstrated here with /home/carlos/secret), traversal of the file system, and — depending on server configuration — full remote code execution. The attack requires no elevated privileges beyond a standard authenticated user account and bypasses any blacklist-based extension filtering entirely.
