Lab 3 — Web Shell Upload via Path Traversal

🟣 Critical 📅 2026-08-03

📋 Finding Summary

FieldValue
TypeWeb App
Severity🟣 Critical
CVE / CWECWE-22, CWE-434
Date2026-08-03

🔍 Description

The avatar upload functionality on the My Account page restricts uploaded files to an avatars/ subdirectory, which is configured to serve files statically without executing PHP. However, the server only strips literal path traversal sequences (../) from the filename while failing to decode URL-encoded variants. By submitting ..%2fexploit.php as the filename in the multipart upload request, an attacker can traverse one directory level up and land a PHP web shell in the /files/ directory, where PHP execution is enabled. A subsequent GET request to /files/exploit.php triggers the PHP engine and returns the output of arbitrary code.

🎯 End Goals

  • Upload a PHP web shell that the server will execute rather than serve as static content.
  • Exploit the URL-encoded path traversal bypass to land the shell outside the avatars/ directory.
  • Use the web shell to read /home/carlos/secret and submit it to solve the lab.

🪜 Steps to Reproduce

  1. Log in as wiener and navigate to the My Account page.
  2. Upload a benign image to confirm the upload mechanism and identify the file-serving path.
  3. Create a PHP web shell that reads /home/carlos/secret.
  4. Upload the PHP file directly to establish that the avatars/ directory does not execute PHP.
  5. Intercept the upload request in Burp Suite and change the filename parameter to use a URL-encoded path traversal sequence (..%2fexploit.php).
  6. Confirm the server preserves the traversal and places the file one level above avatars/.
  7. Issue a GET request to /files/exploit.php to trigger execution and retrieve the secret.
  8. Submit the secret to solve the lab.

🧠 Analysis

Step 1 — Lab setup — logging in and locating the avatar upload form

Navigated to the lab and logged in with the provided credentials (wiener). The My Account page at /my-account presents an avatar upload form that posts files to /my-account/avatar as a multipart request.

Step 2 — Upload a benign image to map the upload directory

Selected image.jpeg and clicked Upload. The server responded with “The file avatars/image.jpeg has been uploaded,” confirming files land in an avatars/ subdirectory. The account page then rendered the image as the current avatar.

Step 3 — Inspect HTTP traffic to discover upload and file-serving paths

In Burp Proxy HTTP history, the POST to /my-account/avatar confirmed the Content-Disposition filename parameter and the avatars/ upload path in the server’s confirmation message. Inspecting the subsequent GET /my-account response body revealed <img src="/files/avatars/image.jpeg">, showing that uploaded avatars are served from the /files/avatars/ URL path.

Step 4 — Create the PHP web shell

Created exploit.php in the Kali working directory containing <?php echo file_get_contents('/home/carlos/secret'); ?> to read the target file upon execution.

Step 5 — Upload the PHP web shell directly

Selected exploit.php and submitted the upload form. The server accepted the file without restriction and responded “The file avatars/exploit.php has been uploaded.” The account page displayed a broken image placeholder where the avatar should appear, as the browser attempted to render the PHP file as an image.

Step 6 — Confirm the web shell is served as static text, not executed

In Burp HTTP history, the GET request to /files/avatars/exploit.php returned HTTP 200 with MIME type text and the raw PHP source code in the response body rather than any output. This confirmed that the avatars/ directory is configured to serve .php files as static content only, and the shell must be placed elsewhere for execution.

Step 7 — Attempt plain path traversal in the filename — blocked

Sent the upload request to Burp Repeater and modified the filename parameter to ../exploit.php. The server responded “The file avatars/exploit.php has been uploaded” — the literal ../ sequence was stripped server-side and the file landed in avatars/ as before.

Step 8 — Bypass the traversal strip with a URL-encoded slash

Changed the filename to ..%2fexploit.php, URL-encoding the / as %2f to prevent the server’s string-matching strip from recognizing the traversal sequence. The server responded “The file avatars/../exploit.php has been uploaded,” confirming the encoded traversal was preserved and the file was placed one level above avatars/ — in the /files/ directory where PHP execution is enabled.

Step 9 — Execute the web shell and retrieve the secret

Opened a second Repeater tab and issued a GET request to /files/exploit.php. The server executed the PHP and returned the contents of /home/carlos/secret: ZU6hGJ8MOgh07Nr9xVUvn9c3pjTlsv1h

Step 10 — Submit the secret and solve the lab

Submitted ZU6hGJ8MOgh07Nr9xVUvn9c3pjTlsv1h via the lab’s Submit solution button. The lab confirmed the value was correct and marked the lab as Solved.

🎯 Impact

An attacker with access to the avatar upload endpoint can upload arbitrary PHP files and, by exploiting the URL-encoded path traversal bypass, execute them in a directory where the PHP engine is active. This achieves server-side code execution under the web server’s process context, enabling arbitrary file read (demonstrated here with /home/carlos/secret), potential traversal across the file system, and — depending on server configuration — full remote code execution. No privilege escalation or additional access beyond a standard user account is required.
