Objective

Observe how the Medium security level behaves compared to Low — determine whether any validation has been added and confirm the upload path is still disclosed on success.

Findings

The File Upload page presents the same form as the Low level. To confirm the upload directory and baseline behavior, a benign image.png was uploaded. The server accepted it and returned the success message ../../hackable/uploads/image.png succesfully uploaded! — confirming that the upload path is still disclosed and the directory remains web-accessible.

PoC:
- Tools used: Browser
- Command: Upload image.png via the form
- Key finding: Benign upload succeeds and discloses the upload path

Exploitation — MIME Type Bypass via Content-Type Header Spoofing

Description

The Medium level validates uploads by checking $_FILES['uploaded']['type'] against an allowlist of image/jpeg and image/png. This value is the Content-Type header submitted by the browser inside the multipart/form-data request — a value the client fully controls and one that has no relationship to the file’s actual content. Because the server trusts this header instead of inspecting the file’s magic bytes, intercepting the upload request with a proxy and overwriting the Content-Type header allows a malicious PHP file to pass the check while keeping its real, executable .php extension.

PoC — Steps to Reproduce

  1. The PHP webshell RCE_2.php (<?php system($_GET['cmd']); ?>) was selected via the Browse button.
  2. With Burp Suite intercepting the request, the first attempt renamed only the filename field to RCE_2.png, leaving the original Content-Type: application/x-php header untouched, then forwarded the request.
  3. The server rejected the upload: Your image was not uploaded. We can only accept JPEG or PNG images. — confirming the check validates the Content-Type header value, not the filename extension.
  4. In Burp Repeater, the request was corrected: the filename was reverted to keep the real .php extension (RCE_2.php), and the Content-Type header was changed to image/png. The request was resent.
  5. The server accepted the file: ../../hackable/uploads/RCE_2.php succesfully uploaded! — the MIME check passed because the Content-Type header matched the allowlist, while the file was stored with its original, executable .php extension.
  6. Navigating to http://127.0.0.1/dvwa/hackable/uploads/RCE_2.php?cmd=id executed the uploaded webshell.
  7. The server returned: uid=33(www-data) gid=33(www-data) groups=33(www-data) — confirming RCE as the web server user.

Lessons Learned

The Medium level’s MIME type check is entirely client-controlled and can be bypassed with any HTTP proxy capable of intercepting and modifying the upload request. $_FILES['uploaded']['type'] reflects the Content-Type header submitted by the browser — it is not derived from the file’s actual content. An attacker who intercepts the request with a tool like Burp Suite can set this header to any value in the allowlist (image/png, image/jpeg) while leaving the malicious file’s real extension in place, so the server saves the upload as an executable script.

The failed first attempt is instructive: renaming only the filename to .png was not enough, because the Content-Type header — not the extension — is what the server actually checks. Once the header was corrected to image/png while the .php extension was preserved, the bypass succeeded immediately.

Robust server-side validation must inspect the file’s magic bytes directly (for example using PHP’s finfo_file()) rather than trusting the client-supplied Content-Type header, and should also enforce a strict extension allowlist independent of that header. The High level addresses part of this gap with an extension allowlist, requiring a different bypass technique.
